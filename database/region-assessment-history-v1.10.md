# 행정구역 자동 재검증·수동 확인 이력 v1.10

2026-09-04 설계 · 2026-09-05 API·배치 및 V10 운영 적용. [운영 반영 보고서](../operations/region-production-result-2026-09-05.md). 전용 관리자 검토 화면도 후속 배포했다. [관리자 검토 배포 보고서](../operations/region-admin-review-release-2026-09-05.md).

## 목적과 범위

v1.8의 좌표 기반 행정구역 판별에 보수적인 추가 검증을 붙이고, 관리자 화면이 나중에 미확정 건과 근거를 조회할 수 있게 한다. 이 v1.10 스키마 설계의 범위에는 관리자 화면·API·승인 동작이 포함되지 않았으며 이후 별도 배포했다. 기존 화장실 주소·기존 좌표는 변경하지 않는다.

## 자동 판정 정책 (`kakao-b-v2`)

### 사용자 확정 운영 정책 — 2026-09-04

- **공공데이터 최초 좌표 생성은 기존 방식 유지**: 주소 검색 결과가 여러 건이어도 기존 수집 서비스의 첫 번째 결과 선택을 유지한다. 정규화 서비스의 추가 교차검증에서 단일 결과를 요구하는 정책과 구분한다. 최초 수집 경로를 단일 결과 전용으로 바꾸는 것을 배포 선행 조건으로 두지 않는다.
- **좌표 없는 기존 데이터는 관리자 좌표 확정을 기다린다**: 정규화 운영 실행에서 `--fill-missing`을 사용하지 않는다. 자동 워커의 `fillMissing=false`를 유지한다. 분석 과정에서 좌표 후보가 계산되더라도 toilet의 빈 좌표를 자동으로 채우지 않는다.
- **좌표 입력/수정 이후 정규화**: 관리자가 좌표를 확정하면 원본 변경 감지에 따라 동일 정규화 엔진이 역지오코딩·교차검증·행정구역/이력 저장을 수행한다. 워커 활성화 후 비동기로 처리되며 입력 순간의 동기 처리라고 보장하지 않는다.
- **정확도 한계 수용**: 첫 검색 결과가 실제 화장실 위치와 다르더라도 같은 시군구 안에 있으면 기본 검증을 통과할 수 있다. VERIFIED는 행정구역 판정이지 실제 입구 위치 인증이 아니다. 정확한 위치는 이후 관리자 확정/사용자 제보로 개선한다.

아래 규칙은 좌표에 대한 **행정구역 판정**의 기준이며, 공공데이터 최초 지오코딩의 첫 결과 선택 정책을 변경하지 않는다.

1. 기본 판정: 기존 좌표의 법정동 역지오코딩 + 주소 지역 일치. 한 주소 일치·다른 주소 명확한 충돌 없음이면 VERIFIED.
2. 기본 미확정/불일치이며 주소가 있으면 `coord2address`와 각 비어 있지 않은 원본 주소의 `search/address`를 추가 호출한다.
3. 각 주소가 정확히 한 결과이고, 유효한 10자리 법정동 코드의 앞 5자리가 좌표의 시군구 코드와 같으며, 검색 좌표가 기존 좌표로부터 50m 이내여야 한다. 좌표→주소의 구조화된 시도/시군구도 좌표→행정구역과 일치해야 한다.
4. 모두 통과하면 STRUCTURED_ADDRESS_CORROBORATED. 기존 문자열 비교 결과가 UNKNOWN/MISMATCH였다는 사실은 그대로 보존한다. 옛 이름을 일괄 치환하지 않는다.
5. 0건·복수 결과·코드 충돌·API 간 지역 충돌·50m 초과는 수동 검토. 50m는 자동 승격 한계일 뿐 오류 판정 기준이나 좌표 이동 허용 범위가 아니다.
6. 네트워크/공급자 실패는 REVERSE_FAILED로 별도 재시도 대상으로 남긴다. 인증/한도 오류는 실행 중단. 주소/좌표 오류와 혼동하지 않는다.

붙어 있는 주소를 임의 문자열 분리만으로 확정하지 않는다. 유니코드 공백은 비교용으로만 정리하고, 누락/붙임 주소는 구조화된 검색 결과로 검증한다. 원본 주소는 보존한다. 기본 지역 일치가 화장실 입구의 위치 정확도까지 보장하지는 않는다.

## 저장 구조

### `toilet_region`: 현재 상태

기존 파생 테이블의 status/reason/result_json을 사용한다. result_json에 다음 evidence를 추가한다.

- reverseAddress: 좌표→주소의 시도/시군구 및 도로명/지번
- maxDistanceMeters: 판정 당시 기준(50m)
- addresses: ROAD/JIBUN별 검색 수, 좌표 후보, 법정동 코드, 반환 도로명/지번, 거리, 개별 사유
- reasons: 모든 보류/실패 사유
- 기존 source, evaluated, roadCheck/jibunCheck, checkedEpochMillis, algorithmVersion도 유지

### `toilet_region_assessment_history`: 이전 판정 보존

| 컬럼 | 한글 의미 | 용도 |
|---|---|---|
| assessment_id | 판정 이력 ID | 독립 식별자 |
| toilet_id | 화장실 ID | 현재 화장실·관리자 상세 연결 |
| source_hash | 분석 원본 지문 | 주소/좌표 변경 판별 |
| algorithm_version | 판정 규칙 버전 | 규칙 변경 전후 구분 |
| status / reason | 판정 상태 / 대표 사유 | 결과 분류 |
| result_json | 전체 판정 근거 | 원본·후보·거리·코드·세부 사유 보존 |
| checked_epoch_millis | UTC epoch 밀리초 | 정확한 시각·재실행 식별 |
| checked_at | 판정 시각(KST) | 관리자 화면 정렬 |

현재 상태 저장과 동일 트랜잭션으로 추가한다. 같은 결과를 재적용하면 중복 삽입하지 않는다. 원본이 분석 이후 바뀌면 현재 상태/이력 모두 저장하지 않고 재분석 대상으로 남긴다. NULL 좌표 채움 전 원본 스냅샷을 이력에 보존한다. 삭제 시 자동 연쇄 삭제하지 않는다. 사용자 이메일·토큰·인증키·HTTP 인증 헤더는 저장하지 않는다.

## 관리자 기능 연결 계약 (추후 구현)

- 대기 목록: 현재 `toilet_region`의 MISMATCH/ADDRESS_UNVERIFIED/NO_COORDINATE/INVALID_COORDINATE. REVERSE_FAILED는 장애/재시도 목록으로 분리.
- 좌표 없음 목록은 현재 toilet의 latitude/longitude 누락으로 별도 조회한다. 분석 후보가 VERIFIED여도 실제 좌표가 비어 있으면 해결된 건으로 취급하지 않는다. `current_toilet_region`에는 확정 좌표와 맞는 결과만 노출된다.
- 상태별 목록은 `WHERE status=? ORDER BY checked_at,toilet_id LIMIT ?` 및 keyset 페이지네이션을 사용한다.
- 상세: toilet_id로 현재 화장실과 연결하고, 이력은 checked_at/assessment_id 순으로 조회한다. 삭제된 화장실은 삭제됨으로 표시한다.
- 목록 노출 때 source 주소/좌표가 현재와 다르면 '위치 변경 후 재검증 대기'로 표시하며 옛 근거로 승인하지 않는다.
- 관리자 수정은 기존 좌표/주소 확정 서비스로 수행하고 정규화 워커가 다시 판정한다. 지역명 직접 덮어쓰기나 판정 근거 수정은 하지 않는다.
- 관리자 검토 완료/보류 상태, 처리자·메모·권한 확인·감사 이벤트는 추후 관리자 API 구현 시 추가한다. 지금 판정 이력은 사람의 승인 이력과 다르다.
- 미해결 근거는 자동 삭제하지 않는다. 운영 전 보관 기간·백업·해결 후 보관/파기 정책을 확정하고, 파일/DB 증가량을 관측해야 한다.

## DDL·인덱스·배포

[분리 DDL](ddl/v1.10-region-assessment-history.sql)은 API V10과 동일하다. V8/V9/V10은 2026-09-05 운영에 함께 반영했다. 기존 적용 migration은 편집하지 않는다.

- 현재 목록: `idx_toilet_region_review(status, checked_at, toilet_id)`
- 화장실별 이전 판정: `idx_region_assessment_toilet(toilet_id, checked_at, assessment_id)`
- 재적용 중복 방지: toilet_id/source_hash/algorithm_version/checked_epoch_millis 유일키

배포 전 백업 → 격리 MySQL에서 V8~V10 검증 → API migration → 제한 dry-run → 결과 확인 후 명시적 apply → 워커 활성화 순서. 설계 당시에는 운영 migration/apply/배포 전이었으며, 후속 실행 결과는 운영 반영 보고서에 기록했다. V10 없이 새 워커 apply를 실행하면 이력 저장 실패로 트랜잭션이 롤백된다.

2026-09-05 전수 분석과 신규/변경 재검증을 완료했다. 최초 운영 반영은 외부 API를 호출하지 않는 전용 RegionReplayCli를 사용한다. [최종 보고서](../operations/region-full-final-review-2026-09-05.md)와 [반영 실행안](../operations/region-production-apply-plan-2026-09-05.md)이 최신 운영 검토 기준이다. 워커도 기본 설정에서는 누락 좌표의 후보 주소 검색을 하지 않고 관리자 입력을 기다린다.

롤백: 워커 중지 → 현재 파생 데이터 백업 → 이전 실행 파일로 복귀. 새 이력 테이블은 보존하는 것을 기본으로 한다. 스키마 철회가 꼭 필요하면 별도 이력 백업·복원 검증 후 V10 인덱스/테이블을 제거하되 Flyway 이력은 임의 삭제하지 않는다. 기존 toilet 주소/좌표는 롤백 대상으로 일괄 수정하지 않는다.

## 실행/재개

기존 호출 간격·일일 예산·3회 제한 재시도·401/403/429 중단을 추가 조회에도 적용한다. 역행정구역은 좌표별 캐시를 재사용한다. 추가 주소 검증은 항목 결과 저장 후 재실행 시 생략되지만, 항목 처리 도중 중단되면 그 항목의 추가 호출은 반복될 수 있다. 호출 예산은 전송 전에 기록한다.

v2는 v1 체크포인트를 유효 판정으로 재사용하지 않는다. 따라서 규칙 변경 후 재분석 호출량을 따로 예산에 반영해야 한다. dry-run은 파일 JSONL만 남기고 DB 이력은 저장하지 않는다. DB 이력은 승인된 apply부터 생성된다.
