# 공공데이터 변경 후보와 관리자 비교 반영

2026-09-13 KST · 개발 4주차(9/7~9/13) · [WBS #99](https://github.com/toilet-project/docs/issues/99)

**계획 문서. 구현·DDL 적용·운영 배포 전이다.** 테이블·필드명은 설계 초안이며, 구현 소요일과 완료일은 아직 정하지 않았다.

## 무엇이 달라지나

관리자가 확정한 위치·주소와 다른 공공데이터가 들어오면, 현재 값을 유지하면서 변경 후보를 남긴다. 관리자는 기존 검토 화면에서 두 값을 비교하고 반영 여부를 결정한다.

| 항목 | 이번 계획 |
| --- | --- |
| 위도·경도·도로명·지번 주소 | `ADMIN_CONFIRMED` 시설은 자동 덮어쓰기 금지, 다른 값은 검토 후보로 저장 |
| 시설명·개방시간·변기 수·편의시설·관리기관 등 | 기존 공공데이터 자동 갱신 유지 |
| 같은 제안의 반복 수신 | 후보 중복 생성 없이 최근 수신 정보 갱신, 실행별 수신 기록은 유지 |
| 관리자 결정 | 변경 반영 / 현재 값 유지 / 나중에 검토 |

“승인 전 정보 유지”는 위 네 보호 항목에 대한 원칙이다. 모든 화장실 필드를 승인제로 전환하는 계획이 아니다.

## 현재 동작과 부족한 점

운영 배치는 관리자 확정 좌표·주소를 보호하지만, 반영하지 않은 공공데이터 값을 별도로 보관하거나 검토 목록에 표시하지 않는다. 배치 이력은 실행별 수신·신규·갱신 집계다. 이 집계나 시설 수정시각만으로 특정 시설의 실제 수신 여부를 증명할 수 없다.

이번 계획은 기존 보호 로직을 없애는 것이 아니라 **변경 제안과 수신 근거를 보완**하는 작업이다. 기존 제보·감사 이력의 기간 삭제, 회원 기능, 자동 복구는 범위에 포함하지 않는다.

## 관리자 사용 흐름

1. 기존 행정구역 검토 화면의 **공공데이터 변경** 목록에서 대기 항목을 연다.
2. 현재 확정값과 새 공공데이터 값을 나란히 비교한다. 달라진 항목만 강조한다.
3. 좌표가 유효하면 지도에 현재 위치·제안 위치와 이동 거리를 표시한다. 주소만 있거나 좌표가 없으면 그 한계를 명확히 보여준다.
4. 변경 반영 또는 현재 값 유지를 선택하고 결정 사유를 남긴다. 나중에 검토는 대기 상태를 유지한다.

목록에는 시설명, 변경 항목, 최초·최근 수신일과 상태를 표시한다. 상세에는 배치 실행, 수신 당시 확정값, 현재 확정값, 제안값, 이전 결정 이력을 표시한다. 상태·기간 필터와 페이지네이션을 제공한다. 첫 버전에는 일괄 승인이나 별도 외부 알림 서비스를 추가하지 않는다.

반영은 좌표·주소를 하나의 일관된 묶음으로 다룬다. 누락 좌표·잘못된 범위·불명확한 주소를 그대로 승인할 수 없으며, 필요하면 기존 관리자 위치 확정 절차에서 보완한다. 주소의 첫 번째 검색 결과를 자동 확정하지 않는다. 기존 역지오코딩 절차가 제안과 다른 최종값을 만들면 저장 전에 최종값을 다시 보여준다.

## DB 구조 초안

기존 `toilet`은 서비스에 노출할 현재 정보를 유지한다. 후보 정보는 별도 저장한다.

| 저장소 | 목적과 주요 정보 |
| --- | --- |
| 기존 `toilet` | 현재 확정 좌표·주소. 배치 자동 덮어쓰기 금지 유지 |
| 신규 `public_data_change_review` | 시설 ID, 수신 당시 확정값·확정 이력 기준, 제안 좌표·두 주소, 변경 항목, 비교 해시, 공급자 갱신시각, 최초·최근 수신시각, 상태, 버전, 처리자·시각·사유, 대체 후보·반영 이력 연결 |
| 신규 `public_data_confirmed_receipt` | 관리자 확정 시설의 실행별 수신 증빙. 실행 키·시설 ID, 수신시각, 입력 해시, 처리 전후 보호값 해시, 결과 분류, 관련 후보 ID |
| 기존 `batch_sync_history` | 전체 배치 집계 유지. 실행 시작 시 발급한 키로 시설별 수신 기록과 연결 |
| 기존 `coordinate_revision` 및 감사 이력 | 실제 반영한 좌표·주소의 변경 전후와 관리자 결정을 기록 |

검토용 주 테이블과 가벼운 수신 연결 테이블을 나누는 이유는 **변경 후보가 없는 동일 값 수신도 확인**하고, 후보가 여러 번 수신되어도 당시 실행과 처리 결과를 잃지 않기 위해서다. 수신 기록 대상은 관리자 확정 시설로 제한한다. 공공데이터 전체 원문을 매번 복제하지 않는다.

수신 당시 확정값과 제안값은 기존 후보에서 덮어쓰지 않는다. 최근 수신시각·횟수만 갱신하며, 제안이나 확정 기준이 바뀌면 새 후보로 구분한다. 해시는 비교 보조 자료이며 후보의 실제 비교값을 대신하지 않는다.

실행 키·시설 ID의 중복 방지, 시설별 최신 대기 후보의 유일성, 상태·수신일 목록 조회 인덱스를 설계한다. 같은 실행 안에서 동일 시설에 상충하는 레코드가 나오면 순서로 임의 확정하지 않고 충돌로 기록한다. 기존 확정 이력의 필수 `report_id`·허용 source 등을 최신 스키마에서 확인하며, 공공데이터 검토를 위해 가짜 사용자 제보를 만들지 않는다.

보관량·인덱스·증가 속도와 운영 보관 기준은 DDL 확정 전에 검토한다. 이번 계획으로 기존 이력을 삭제하거나 새 자동 삭제 정책을 도입하지 않는다. 처리자 참조·사유의 개인정보 처리는 기존 계정·감사 정책을 따른다.

## 배치 처리와 중복 규칙

- **비교 시점:** 기존 지오코딩 보존 처리로 공급자 좌표가 가려지기 전에 원래 수신값을 확보한다. 최종 판단은 저장 트랜잭션 안에서 최신 확정 상태를 다시 읽고 수행한다.
- **동등 판정:** 좌표는 저장 정밀도, 주소는 사전에 정한 공백·NULL 규칙으로 비교한다. 거리만으로 서로 다른 주소를 같다고 처리하거나 숫자·동호 정보를 제거하지 않는다. 누락값과 실제 변경은 구분해 표시한다.
- **같은 값:** 후보를 만들지 않지만 해당 실행에서 실제로 수신했고 보호값이 유지됐다는 기록은 남긴다.
- **다른 값:** 운영 보호값은 그대로 두고 후보와 수신 기록을 저장한다. 다른 일반 필드의 기존 자동 갱신은 유지한다.
- **반복 제안:** 동일한 확정 기준·제안이면 같은 후보에 수신 사실을 연결한다. 이전에 현재 값 유지를 결정했다면 매일 새 대기로 되살리지 않는다.
- **새 제안/원복:** 제안이 바뀌면 이전 대기를 대체 처리한다. 공급자 값이 현재 확정값과 같아지면 불필요한 대기를 종료하고 `공공데이터 일치` 사유를 남긴다. 예전에 거절한 값으로 돌아오면 같은 확정 기준의 기존 결정을 재사용한다.
- **관리자 재수정:** 현재 확정값이나 확정 이력 기준이 바뀌면 예전 거절 결정을 무조건 재사용하지 않는다. 최신 기준으로 비교한다.

후보·수신 기록과 해당 페이지의 화장실 처리를 같은 트랜잭션으로 묶는다. 기록 실패를 삼키고 갱신 성공으로 집계하지 않는다. 페이지 일부만 먼저 커밋된 뒤 배치가 실패하면 커밋된 수신 기록과 실패한 실행 상태를 구분한다. 롤백된 페이지를 수신·처리 완료로 표시하지 않는다. 재시도에는 실행 키와 유일성 제약을 사용한다.

## 상태·승인 안전장치

| 상태 | 의미 |
| --- | --- |
| `PENDING` | 관리자 검토 대기. 나중에 검토는 이 상태 유지 |
| `APPLIED` | 관리자 확인을 거쳐 반영 완료 |
| `KEPT_CURRENT` | 해당 확정 기준과 제안에 대해 현재 값 유지 결정 |
| `SUPERSEDED` | 새 제안·새 확정 기준·공공데이터 원복 등으로 더 이상 승인할 수 없는 후보. 사유와 대체 후보 연결 유지 |

관리자 API는 기존 ADMIN 권한을 사용한다. 목록·상세와 상태를 바꾸는 요청을 분리하고, 결정 요청에는 후보 버전과 확정 기준을 포함한다. 다른 관리자 수정, 새 제안 수신, 중복 클릭이 있으면 잠금/버전 검사로 오래된 승인을 차단하고 다시 비교하도록 안내한다.

변경 반영 시 `toilet` 갱신, `coordinate_revision` 기록, 후보 처리와 감사 기록을 하나의 트랜잭션으로 묶는다. 반영 후에도 `ADMIN_CONFIRMED`를 유지한다. 트랜잭션이 성공한 뒤 기존 행정구역 재판정과 관련 상세 캐시 갱신 경로를 연결하고, 재시도해도 확정 이력이 중복되지 않게 한다. 현재 값 유지는 보호값·확정 이력을 바꾸지 않으며 결정 기록만 남긴다.

## 구현·검증 순서

1. **DB:** 최신 스키마와 이력 연결 확인 → DDL·인덱스·실행 키·용량 기준 확정.
2. **배치:** 원본 비교·후보·수신 기록·중복 처리·실패 일관성 구현.
3. **API:** 관리자 목록·상세·결정, 권한·동시 수정 보호·이력·재판정 연결 구현.
4. **관리자:** 기존 화면 안의 목록·비교·지도·결정 UX 구현 및 프리뷰 확인.
5. **검증:** 합성 데이터로 동일 값, 신규 제안, 반복, 거절 후 반복, 새 제안, 공급자 원복, NULL, 좌표 오류, 동시 승인·수신, 부분 실패·재시도, 권한 거부를 확인.
6. **배포 준비:** 호환되는 추가 DDL → API → 배치 → 관리자 순서를 구체화하고 기존 값 보호·중단·이전 버전 복귀를 확인. 공개·운영 적용은 별도 사용자 승인 후 수행.

운영 서버에 시험용 DB를 만들거나 실제 시설을 시험값으로 수정하지 않는다. SQL 검증은 운영과 자원이 분리된 로컬 또는 CI의 합성 데이터로 진행한다. 임시 파일·컨테이너는 검증 후 정리한다. 복귀할 때 새 후보·수신 기록을 삭제하거나 테이블을 즉시 DROP하지 않는다.

## 10월 점검과의 관계

[DOCS #95 — 10월 초 운영 점검](https://github.com/toilet-project/docs/issues/95)은 실제 수신·upsert 이후 보호 결과를 관측하는 별도 항목으로 유지한다. 이번 구현이나 합성 시험만으로 완료 처리하지 않는다. 실제 수신 증거가 먼저 확보되면 조기 검증할 수 있지만, 10월 점검 일정을 임의 변경하거나 자동 실행을 예약하지 않는다.

2026-09-13 조기 점검에서는 새벽 2시 배치의 수신 142건·신규 2건·갱신 140건·실패 0건을 확인했다. 같은 기간의 **현재 API 재조회** 142건에는 관리자 확정 시설이 없었고, 기존 검증 대상의 좌표·두 주소·확정 상태·행정구역 조회는 정상이었다. 현재 재조회는 당시 수신 원본 증거가 아니므로 보존 실증 완료로 판정하지 않았다.

이 계획의 수신 기록이 추가되면 특정 시설의 실행 키·입력·처리 전후 보호값을 연결해 자연 운영 검증에 사용할 수 있다. 검토 후보 자체가 없었다는 이유만으로 미수신이라고 단정하지 않는다. [BATCH #35](https://github.com/toilet-project/toilet-batch/issues/35)의 기존 구현 완료 상태는 유지한다.

## 완료 기준과 공개 범위

계획 문서 게시와 WBS 등록은 설계 정리의 완료다. 실제 기능 완료는 위 구현·검증·승인 배포 항목으로 별도 관리한다. 시설의 자연 수신 대기가 남으면 #95에 연결하고, 관측하지 않은 결과를 성공으로 체크하지 않는다.

공개 문서에는 실제 시설별 원문·관리번호·전체 비교 목록·사용자 정보·비밀값을 넣지 않는다. 실제 운영 증빙은 필요한 최소 항목만 접근 제한된 경로에 보관하며 공개 WBS에는 집계·판정·남은 조건만 기록한다.
