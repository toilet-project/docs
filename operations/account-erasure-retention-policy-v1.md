# 백업·변경 로그·파기 대장 보관 및 정리 절차 v1

상태: 2026-09-06 **기술 정책안 및 순수 dry-run 판정 코드**. 운영 보관 설정 변경, 백업/로그/R2 삭제, 자동 정리 스케줄 등록은 하지 않았다. 이 문서는 법적 보유 근거나 개인정보처리방침의 시행을 대신하지 않는다.

## 확인한 사실과 선택한 기준

| 대상 | 현재 확인 | v1 운영 목표 / 제한 |
| --- | --- | --- |
| 사용자 수동 복사 백업 | 사용자가 별도 사본 없음 확인 | 새 사본·외부 복제·스냅샷 도입 시 목록과 정책 갱신 |
| 암호화 SQL 덤프 | 매일 03:15 KST, 기본 14일. 약 15일 경과 뒤 다음 백업 성공 시 정리 | 14일 경과 대상은 백업 성공 여부와 독립적으로 정리·검증하도록 후속 구현. 현재 적용 아님 |
| MySQL binlog | 8.0.46, log_bin=1, expire_seconds=2592000, auto_purge=1 | 30일 설정 유지안. 설정이 아닌 실제 제거 확인 필요 |
| R2 파기 의도 | DB 삭제 **전** 암호화 선기록 | 객체 생성 시각 기반 TTL 금지 |
| R2 정리 검토 | 삭제 완료의 영구 확인 증빙은 아직 없음 | 최초 신뢰 가능한 DB 부재 확인 후 최소 32일 + 관련 사본 제거 증빙 |

32일은 현재의 더 긴 로그 보관 30일에 점검 여유 2일을 더한 **최초 검토 가능 시점**이다. 회원 복구 기간인 달력상 3개월과 별개다. 32일 뒤 무조건 삭제하거나, 모든 사본이 32일 내 없어진다고 보장하는 의미가 아니다. 로그/백업 보관을 늘리면 v1 판정 자체를 보류하고 정책부터 개정한다.

MySQL 자동 만료는 시작/로그 flush 등 시점에 수행될 수 있으므로 설정값만 보고 실제 로그가 사라졌다고 판단하지 않는다. 자동 purge가 켜져 있어도 파일 목록과 복제·복구 사용 여부를 확인해야 한다. [MySQL 공식 문서](https://dev.mysql.com/doc/refman/8.0/en/purge-binary-logs.html)

## 정상 흐름과 실패 흐름

1. API 또는 배치가 파기 대상의 R2 의도를 선기록하고 읽어 검증한다. 기존 코드 유지.
2. Redis 정리와 SQL 트랜잭션이 끝난다. 트랜잭션 내부의 삭제 호출 성공만으로 COMMIT 성공을 판정하지 않는다.
3. 별도 읽기 트랜잭션으로 같은 realm·회원 ID·생성 시각의 계정 부재를 확인한다. 동일 ID에 다른 계정이 있으면 충돌로 보류한다. COMMIT 응답을 잃었더라도 새 부재 확인 이후부터 보수적으로 시간을 센다.
4. 신뢰 가능한 최초 부재 확인 시각을 암호화된 **별도 완료 증빙**에 영속화한다. 재시도마다 최초 시각을 앞당기거나 덮어쓰지 않는다. 부재를 처음 확인한 시각보다 이른 SQL 실행 시각·의도 생성 시각으로 소급하지 않는다.
5. 32일이 지난 뒤 최신 사본 목록과 대장 독립 목록을 대조한다. 관련 원본/사본 제거가 확인되지 않으면 원인 코드와 건수를 남기고 보류한다.
6. 정리 검토를 통과해도 삭제 실행 직전에 배치·즉시 파기·복원·백업과의 충돌 방지 및 최신 증빙을 다시 확인해야 한다. dry-run 결과는 삭제 권한이 아니다.

예: 9월 1일에 의도 작성, DB 장애로 9월 20일에 부재를 처음 확인했다면 최초 검토 시점은 10월 22일이다. 9월 1일을 기준으로 30일 TTL을 설정하지 않는다.

### 완료 증빙과 독립 목록의 후속 구현 계약

- 완료 증빙은 의도 객체와 분리한다. 최소 필드: 형식 버전, realm, 의도 식별자/해시, 최초 부재 확인 UTC 시각, DB 복원 세대 식별자, 사용 암호화 키 ID. 이메일·소셜 원문·제보 원문은 넣지 않는다. 암호화·인증된 읽기 검증·조건부 최초 쓰기를 사용한다.
- R2 기록 후 SQL 실패는 미완료로 유지한다. SQL 성공 후 증빙 쓰기 실패는 재수집하여 나중 시각으로 기록한다. 이 경우 정리는 늦어질 수 있지만 대장을 먼저 삭제하지 않는다.
- 증빙을 운영 DB에만 저장하면 복원 시 같이 되돌아가므로 R2 등 별도 장애 영역에 둔다. 현재 `v1/<realm>/` 의도 목록과 섞지 않아 기존 복원 도구의 건수 검증을 깨뜨리지 않는다.
- 독립 목록은 실시간 R2 LIST 결과를 그대로 기대값으로 쓰지 않는다. 검증된 이전 세대와 신규 선기록/완료/정리 변경을 연결한 목록 및 해시·세대 번호가 필요하다. 목록이 누락되거나 복원이 감지되면 정리를 차단한다.
- 대장 정리에는 순서가 있는 정리 계획 → 정확한 객체 버전/해시 재확인 → 삭제 → 남은 객체·목록 검증이 필요하다. 중간 장애를 재개할 수 있어야 한다. 일부 삭제 후 기대 건수만 줄여 복원 검사를 통과시키지 않는다.
- 완료 증빙·회원과 연결 가능한 목록/정리 계획도 개인정보 관리 대상이다. 검증 완료 후 함께 정리하며, 공개 로그에는 정책 버전·집계 건수·고정 실패 코드만 남긴다. 암호화 키는 해당 키를 쓰는 보존 대상이 0임과 복구 가능 여부를 확인하기 전 제거하지 않는다.

위 증빙 저장·독립 목록·정리 실행기는 **아직 미구현**이다. 이번 코드는 주어진 증빙의 조건을 판정할 뿐 실제 증빙을 수집하거나 진위를 검증하지 않는다.

## 실제 사본 제거 확인의 범위

덤프 파일 날짜 하나로 원본 개인정보의 시점을 증명하지 않는다. 장기 실행 백업은 삭제 전에 시작해 삭제 후 완료될 수 있고, 파일 복사는 mtime을 바꿀 수 있다.

- 백업 목록에는 암호화 파일 해시, DB/스키마/복원 세대, 캡처 시작·종료 시각, 생성 작업, 보관 위치 및 제거 확인을 기록한다. 기존 메타데이터 없는 백업은 보수적으로 관련 사본으로 취급한다.
- 삭제 전 시작한 스냅샷/미완료 백업, 오래된 read transaction에서 내보낸 덤프, 복제 지연 사본도 포함한다. 한 디렉터리의 파일이 없다는 것만으로 `사본 제거 완료`를 주지 않는다.
- binlog는 파일 이름/활성 로그/보존 범위와 복구 체인을 확인한다. 파일 mtime이나 30일 설정만으로 내용의 시점을 단정하지 않는다. 읽기 검증은 이벤트의 개인정보 원문을 로그에 출력하지 않는다.
- Redis 지속성 파일, OS/디스크 스냅샷, 관리자 임시 덤프·복호화 파일의 존재 여부도 확인한다. 사용자 수동 복사가 없다는 답변으로 이 범위를 생략하지 않는다.
- 백업·복원 또는 DB 세대 변경이 진행되었으면 이전 확인은 무효다. 격리 복원에서는 필요한 로그 재생까지 마친 뒤 대장을 재적용하고, 그 후 이전 로그를 다시 재생하지 않는다.

## 덤프·로그 만료 작업 설계

후속 운영 도구는 기본 dry-run이어야 하며 삭제 적용은 별도 승인을 받는다.

1. 기존 백업 생성과 독립된 systemd 점검/정리 작업을 두고 공유 잠금으로 충돌을 막는다. 배치나 새 백업 실패 때문에 만료 점검까지 생략하지 않는다.
2. 삭제 후보는 사전에 승인한 정규 경로 아래의 정확한 파일 ID·해시 목록으로 한정한다. 링크·하위 임의 경로·부분 생성 파일·사용 중인 복원 원본은 보류한다. 광범위한 glob/디렉터리 삭제를 쓰지 않는다.
3. 신뢰 가능한 생성/캡처 메타데이터를 기준으로 14일을 계산한다. 최근 정상 백업 부재와 보관 초과를 모두 경보한다. 오래된 유일 백업을 조용히 영구 보관하거나, 승인 없이 제거하지 않는다. 장기 실패 시 복구성과 파기 기한의 충돌을 운영자가 처리하도록 한다.
4. binlog의 기존 30일 설정을 유지하되 실제 만료가 지연되면 점검한다. 복제본/복구 작업이 필요로 하는 로그를 확인하지 않은 상태에서 강제 purge/flush하지 않는다. 파일 직접 삭제나 RESET MASTER는 사용하지 않는다.
5. 제거 후 목록을 다시 수집해 관련 사본 없음이 확인될 때만 정리 검토 증빙을 충족시킨다. 설정값·실행 exit 0만으로 증빙을 발급하지 않는다.

## dry-run 정책 코드

batch `ErasureRetentionReviewPolicy`는 Spring bean이나 스케줄러가 아닌 독립된 순수 함수다. 운영 삭제 경로에서는 호출하지 않는다.

입력: UTC `Instant`인 최초 부재 확인 시각, 최신 증빙 점검 시각, 아래 8개 검증의 충족 여부. 각 충족 여부는 같은 대상·realm·일관된 목록에 대한 **검증된 호출자 입력**이어야 한다.

1. v1 보관 설정 및 실제 만료 처리 정상
2. 모든 사본 위치 목록 확인
3. 파기 전 정보를 포함할 수 있는 사본/로그 제거 확인
4. 현재 DB 부재 재확인
5. 최초 확인 이후 복원 없음
6. 진행 중인 백업/복원 없음
7. 독립 파기 대장 목록 대조 완료
8. 키 복구 검증 완료

결과:

| 코드 | 의미 |
| --- | --- |
| HOLD_INVALID_OR_MISSING_TIME | 시각 누락·역전·미래 값·범위 초과 |
| HOLD_STALE_EVIDENCE | 증빙 점검 후 24시간 초과 |
| HOLD_MINIMUM_DELAY | 최초 부재 확인 후 32일 미경과 |
| HOLD_MISSING_EVIDENCE | 8개 중 하나 이상 미확인. 누락 목록도 반환 |
| REVIEW_CANDIDATE | 검토 후보일 뿐, 실행 전 새 검증·충돌 방지 필요 |

증빙 24시간 기준은 목록 검토용이다. 실제 삭제 직전 증빙을 24시간까지 재사용해도 된다는 뜻이 아니다. 어떤 결과도 DB/R2/파일을 수정하지 않는다.

## 장애 알림과 보관 초과 대응안

기존 Discord 경로를 재사용할 계획이며 이번 변경으로 전송을 연결하지 않았다.

- 매일 점검 결과: 삭제 부재 확인 대기, 32일 경과 후 보류, 가장 오래된 지연 일수, 백업 만료 실패, 목록 불일치, 키 복구 미확인 건수.
- 목록 불일치·잘못된 DB 세대·필수 키 누락은 즉시 경보하고 정리 차단. 동일 장애 반복은 묶어 보내되 미해결 상태를 유지한다.
- 정상 기간 내 보존은 경보하지 않는다. 32일이 지나도 정리 조건을 충족하지 못하면 다음 점검부터 사고/보관 초과로 관리하고 영구 보관 상태로 방치하지 않는다.
- 서버가 꺼지면 자체 타이머도 못 도므로 외부에서 마지막 점검 성공 시각을 감시하는 연결이 필요하다.

R2의 객체 나이 기반 lifecycle은 사용하지 않는다. 보존 잠금은 우발 삭제를 방지할 수 있지만 완료 증빙·조건부 정리를 대체하지 못하며 관리자에 의해 바뀔 수 있다. 운영 prefix에만 적용하는 별도 보호안을 검토하고 가상 시험 영역과 분리한다. 아직 잠금을 변경하지 않았다. [Cloudflare 공식 문서](https://developers.cloudflare.com/r2/buckets/bucket-locks/)
