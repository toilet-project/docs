# 회원 파기 실제 MySQL 검증 — 2026-09-06

상태: **로컬 MySQL 검증 완료. 운영 배포/DDL/회원 삭제/원격 push는 하지 않았다.**

## 격리 환경

- 설치된 MySQL Community 8.0.25 실행 파일을 재사용했다. 기존 MySQL80 Windows 서비스는 중단하거나 설정을 변경하지 않았다.
- 새 임시 datadir, 127.0.0.1 전용 43317 포트, X Protocol 비활성, binlog 비활성, KST(+09:00), 합성 데이터만 사용.
- 테스트 연결은 기본 MySQL 포트 3306을 거부하고 실제 datadir 이름 및 매 실행 생성한 fixture marker를 읽어 일치한 경우에만 무작위 전용 스키마를 생성한다.
- 네트워크 공개 및 운영 DB 복제 없음. 빈 비밀번호 root는 이 임시 합성 DB에서만 사용했다.
- 검증 후 임시 서버를 정상 종료했다. 기존 MySQL80 서비스는 계속 Running임을 확인했다. 합성 데이터와 테스트 결과는 로컬 임시 디렉터리에 남겼다.

운영에서 과거 확인한 버전은 8.0.46이므로 **운영과 동일 버전 검증은 아니다.** 운영 전체 스키마와 새로운 회원 참조/FK 확인도 별도다.

MySQL DDL 검증은 toilet ID 기본 테이블과 실제 V1/V2/V4/V5/V7/V11 마이그레이션을 사용했다. 모든 운영 테이블·V3/V6/V8~V10·운영 트리거까지 복제한 검증은 아니다.
배치 테스트는 회원 관련 FK를 가진 합성 스키마이며 API와 동일한 파기 SQL을 실행했다.
Redis는 모의 객체로 실패/성공을 검증했으며 실제 운영 Redis 연결은 하지 않았다.

## 확인 내용

- V11의 기존 FK 컬럼 NULL 허용 변경과 account_withdrawal 생성 성공.
- 제보가 연결된 상태의 회원 직접 DELETE 거부, 연결 제거 후 제보 유지.
- 복구 선택 동의/3개월 달력 계산/동일 ID 복구/USER만 복구/재동의.
- 기한 만료 복구 거부, 즉시 파기, 반복 요청, 기존 탈퇴자 미편입.
- Redis 실패 시 DB 유지, 미확인 FK가 있으면 파기 SQL 전체 롤백 및 체크포인트 저장.
- 배치 keyset 순회 및 실패한 건을 보존한 재시도.
- 복구가 먼저 회원 행 잠금을 잡으면 파기는 대기 후 ACTIVE 상태를 다시 읽고 삭제하지 않음.

## 발견한 테스트 환경 차이와 보완

1. 새 native MySQL은 이름 기반 시간대 테이블이 없어 Asia/Seoul 세션 설정이 실패했다. 테스트 연결을 동등한 +09:00으로 명시했다. 운영 설정을 바꾼 것이 아니다.
2. H2에서 사용하던 컬럼 인라인 REFERENCES 문법은 MySQL에서 의도한 FK 오류 검증을 보장하지 못한다. 테스트 fixture를 명시적인 FOREIGN KEY 제약으로 변경해 실제 롤백을 확인했다.
3. H2/native 환경을 바꿨는데 Gradle이 이전 테스트 결과를 재사용하지 않도록 marker/port를 test task 입력으로 등록했다.

## 실행

격리 서버와 marker 검증 테이블을 먼저 준비한 상태에서만 다음 환경 변수를 사용한다.
실제 DB 설정이나 운영 비밀번호를 여기에 넣지 않는다.

```powershell
$env:ACCOUNT_RETENTION_MYSQL_MARKER = '<이번 임시 datadir 이름의 10자리 marker>'
$env:ACCOUNT_RETENTION_MYSQL_PORT = '43317'

# API
./gradlew.bat test --tests '*AccountWithdrawalNativeMySqlTest' --tests '*AccountLifecycleIntegrationTest'
# batch
./gradlew.bat test --tests '*AccountErasureWorkerTest'
```

기본 실행에서는 두 환경 변수를 해제하고 H2/모의 객체 회귀를 실행한다.
네이티브 테스트는 매번 새 무작위 스키마를 만들며 기존 로컬/운영 스키마를 DROP하지 않는다.
