## 주요 발견과 필요한 보완

### 1. V1.11은 현재 자동 Flyway 실행 대상이다

운영 `flyway_schema_history`는 baseline 0과 V1~V10 모두 성공이며 V11은 없다. API에는 Flyway starter와 `db/migration/V11__account_withdrawal_retention.sql`이 있고, 실행 환경에 `SPRING_FLYWAY_ENABLED=false` 설정은 없다. 따라서 현재 설정을 그대로 배포하면 V11은 새 API 기동 시 실행될 것으로 판단한다.

- 권장 적용안: **승인된 배포에서 Flyway 한 경로로 V11을 실행**하고 수동 DDL은 별도로 실행하지 않는다.
- 수동 DDL을 먼저 실행한 뒤 동일 V11을 자동 실행하면 컬럼/테이블 중복 오류로 기동에 실패할 수 있다. 이력 임의 INSERT, checksum 덮어쓰기 또는 무조건 `repair`로 우회하지 않는다.
- 수동 설치를 원한다면 기존 Flyway 이력과 일치하는 별도 migration 전략부터 승인받아야 한다.
- MySQL DDL은 여러 문장이 한 트랜잭션으로 롤백되지 않는다. 부분 실패 시 어느 문장까지 적용됐는지 점검한 뒤 전진 복구한다. V11 전체를 무조건 재실행하지 않는다.
- 운영 계정의 권한 출력에는 `toilet_db` 패턴의 ALL PRIVILEGES가 보였지만, 이번에 운영 DDL을 실행해 권한을 시험하지는 않았다. 격리 검증은 임시 DB root로 수행했다.

### 2. R2 키는 GitHub에 있지만 운영 실행 환경에는 전달되지 않는다

API·배치 저장소에 아래 세 시크릿 **이름**이 등록된 것은 확인했다. GitHub에서 값은 읽을 수 없으며 이번에 키 유효성을 재시험한 것은 아니다.

- `ERASURE_LEDGER_ACCESS_KEY_ID`
- `ERASURE_LEDGER_SECRET_ACCESS_KEY`
- `ERASURE_LEDGER_KEYS_JSON`

그러나 두 배포 워크플로의 `.env` 생성 부분에는 이 값과 endpoint/realm/bucket/active-key-id 전달이 없다. 현재 운영 컨테이너에도 해당 자격 증명 환경변수가 없다. 각 repository의 수동 R2 검증 workflow에만 시크릿이 연결되어 있다. **시크릿 등록만으로 운영 연결이 끝난 것은 아니다.**

활성화 전 필수 보완:

1. 값 노출 없이 두 배포 경로에 같은 운영 R2 설정/키를 연결한다.
2. 활성화 요청 시 필수 키·endpoint·JSON/key-id 구성·catalogue 설정을 검사해 누락을 배포 전에 거부한다.
3. 초기 실제 대장 목록/독립 체크포인트·DB 복원 세대를 확인한다. 현재 목록이 비어 있다고 가정하거나 관측값을 곧바로 기대값으로 복사하지 않는다.
4. 값과 객체 원문은 Git/로그/보고서에 넣지 않는다.

### 3. 배치 Redis 설정은 아직 준비되지 않았다

운영 API와 배치 컨테이너의 Redis 관련 설정은 일치하지 않았다. feature 배포 파일에는 `REDIS_HOST=redis`, 포트, 비밀번호 전달이 추가돼 있지만, `toilet-batch`의 repository secret 목록과 이 저장소에 제공되는 organization secret 조회에서 `REDIS_PASSWORD`를 확인하지 못했다. API 저장소에는 있다.

운영 API가 사용하는 **같은 비밀번호**를 배치에 안전하게 연결하고, 같은 Redis 인스턴스/DB 및 refresh·recovery 키 namespace 정리를 검증해야 한다. 새 비밀번호를 임의 생성하거나 Redis 전체 키를 지워 맞추지 않는다. 값은 채팅으로 받지 않는다. 비활성 배치의 Redis 설정 부재 자체를 현재 운영 장애라고 판정한 것은 아니다.

### 4. 기능 OFF는 무영향 배포나 전체 긴급 정지 스위치가 아니다

| 설정/경로 | 현재 feature 코드 동작 | 배포 전 판단 |
| --- | --- | --- |
| API `ACCOUNT_RETENTION_ENABLED=false` | `/withdrawal-options` 비활성 표시, `DELETE /auth/me`는 503 | 기존 탈퇴 기능도 점검 상태로 바뀐다. 무영향 배포로 설명하면 안 됨 |
| 복구 `/auth/recovery` | 위 플래그 검사 없음 | 이미 발급된 복구 증명/기존 복구 대기 계정이 생긴 이후, 플래그 OFF만으로 복구·즉시 파기 전체를 멈출 수 없음 |
| OAuth 로그인 | WITHDRAWN 계정의 복구 판정·기한 경과 파기 경로에 위 플래그 검사 없음 | 활성화 후 긴급 중지 정책을 별도로 마련해야 함 |
| batch `ACCOUNT_ERASURE_ENABLED=false` | 정기 후속 파기 실행 전 return | 현재 배포 파일은 false 고정. API에서 실행되는 즉시 파기는 제어하지 않음 |
| `ERASURE_LEDGER_ENABLED=false` | 파기 대장 요청 시 예외, SQL 파기 진행 안 됨 | 기존 즉시 탈퇴 접수가 완료됐으나 파기 재시도 상태로 남을 수 있어 이것만으로 정상 운영을 구성하지 않음 |

권장 보완은 신규 탈퇴/복구/실제 파기의 중지 범위를 명확히 분리하고 모든 관련 진입 경로에 적용하는 것이다. 기존 탈퇴 기능을 유지하는 호환 배포를 구현할지, 제한된 점검 시간에 웹 안내와 함께 전환할지는 운영 적용안에 명시해야 한다. 이미 WITHDRAWN/복구 대기 계정이 생긴 뒤 예전 OAuth 코드로 되돌리는 것은 안전한 일반 롤백이 아니다.

### 5. 웹·정책과 백업 운영 준비도 함께 필요하다

로컬 웹 feature에는 선택 동의와 복구 UI가 있지만 공개 운영 반영은 이번에 하지 않았다. API만 먼저 활성화하면 이전 웹은 보관 동의를 보낼 수 없고, 사용자에게 복구 선택 흐름이 완성되지 않는다.

- 선택 동의 기본 미선택, 거부 시에도 탈퇴 가능, 달력상 3개월, ADMIN 자동 복구 금지, 실패 시 파기 완료로 표시하지 않는 UI를 함께 검증한다.
- 정책 초안에는 3년 제보/감사 보관 등이 있지만 해당 만료 자동 정리는 이 feature 범위에서 완료되지 않았다. 정책 약속과 실제 운영의 일치를 별도 확인해야 한다. 본 문서는 법률 적합성 심사 결과가 아니다.
- 최근 백업에는 캡처 metadata/DB 복원 세대가 없다. 가상 재파기 통과는 실제 R2 대장 전체 재생·초기 기준 검증 완료가 아니다.
- 완료 증빙 수집, 독립 체크포인트, 새 백업/만료 점검 스크립트·실패 알림은 도구 수준 검증과 영구 운영 연결을 구분한다. 새 백업 스크립트만 교체하면 기존 만료 정리가 없어져 파일이 계속 쌓일 수 있다.

API 선택 회귀는 H2/Mockito 등 로컬 환경을 포함하며, 운영 MySQL+실제 Redis+OAuth/R2 통합 재시험을 의미하지 않는다. 배치 최초 실행은 `UP-TO-DATE`여서 `--rerun-tasks`로 실제 재실행했다. 건너뛴 외부 환경 검사는 통과로 계산하지 않았다. Java 컴파일 deprecation/unchecked 안내와 JVM 클래스 공유 경고는 남지만 테스트 실패는 없었다.

첫 운영 사전 점검은 Flyway baseline의 비파일명 script 값을 파일명으로만 제한한 검사 때문에 중단됐다. 진단 도구의 표시 검사를 보완해 같은 SELECT 점검을 재실행했다. 운영 데이터를 수정해 해결한 것이 아니다.
