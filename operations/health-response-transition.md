# 서비스 상태 확인 응답 전환

관련 WBS: [DOCS #97](https://github.com/toilet-project/docs/issues/97).

## 응답 계약

| 상태 | HTTP 상태 | JSON 본문 | 캐시 정책 |
| --- | --- | --- | --- |
| DB 연결 확인 성공 | 200 | `{"status":"UP"}` | `Cache-Control: no-store` |
| DB 연결 확인 실패 | 503 | `{"status":"DOWN"}` | `Cache-Control: no-store` |

본문에는 상태만 포함한다. 예외 내용과 환경별 이름을 응답에 추가하지 않는다. 이 검사는 DB 연결 확인이며 서비스의 모든 기능을 검증하는 종합 시험은 아니다.

## 적용 순서

1. 실제 실행 중인 감시 버전과 저장소 버전 차이를 확인한다. 운영에만 존재하는 기존 보완을 덮어쓰지 않는다.
2. 외부·내부 감시와 배포 검사가 이전 정상 응답과 새 정상 응답을 모두 인식하도록 먼저 적용한다.
3. API·관리자 이미지를 각각 검증한 뒤, 기존 환경과 사용자 기능을 보존하는 배포 절차로 반영한다.
4. 공개·내부 상태 확인, 감시 결과와 일반 서비스 조회를 확인한다.

HTTP 오류나 `DOWN`, 예상하지 않은 JSON 구조를 정상 판정하지 않는다. 외부 감시의 캐시된 응답 거부도 유지한다.

## 되돌리기와 호환성 종료

API 이미지 되돌리기는 검증된 이전 이미지와 현재 배포 절차를 사용한다. 이전 응답을 읽는 호환 코드는 이미지 되돌리기 기간에도 유지한다. 감시만 이전 버전으로 되돌려 새 API 응답을 오판하는 조합을 만들지 않는다.

이전 이미지가 복구 대상에서 제외되고 모든 감시·배포 검사가 새 계약을 사용하는 것이 확인되면 이전 응답 지원을 제거할 수 있다. 일정만으로 자동 제거하지 않는다.

## 검증

- API·관리자: 상태 확인 HTTP 계약 테스트로 정상/연결 실패/연결 종료 실패와 캐시 금지를 검사한다.
- API 배포: 이전·새 정상 응답, 실패 본문, HTTP 실패를 검사한다.
- 감시: 이전·새 정상 응답과 비정상 본문을 확인하고, 외부 감시는 캐시 응답을 계속 거부한다.
- 셸 감시 시험은 가상 명령으로 실행하며 운영 접속·알림 전송을 하지 않는다.

구현·운영 반영 결과는 WBS에 별도로 기록한다. 인증 정책 후속 검토는 [API #107](https://github.com/toilet-project/toilet-api/issues/107)에서 관리한다.
