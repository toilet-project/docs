| REVERSE_FAILED (법정/행정 코드 충돌) | 7 |

자동 검증 통과는 지역 수준의 근거 일치이며 화장실 입구의 정확도를 보증하지 않습니다.
검토 309건 + 좌표 입력 대기 1,288건 = 1,597건이며 좌표 오류 확정 건수가 아닙니다.
전수 분석 및 후속 외부 호출은 46,831회, 기록 응답을 재생한 운영 적재의 외부 호출은 0회였습니다.
원본 주소·좌표·출처 변경/삭제는 0건입니다.

## 3. 관리자 API

기본 경로: `/api/admin/v1/regions`. ADMIN만 접근 가능하며 비로그인 401, 일반 사용자 403입니다.

| 메서드·경로 | 역할 |
| --- | --- |
| GET 기본 경로 | 상태·검색 기반 목록, page=0, size=20, 최대 100 |
| GET /{id} | 현재 원본, 최근 판정 당시 정보, 구조화된 JSON 근거 |
| GET /{id}/history | 개별 이력, page=0, size=10, 최신순 |
| POST /{id}/coordinates | 좌표 확정, 필수 사유 및 expectedLocation |

필터는 REVIEW(기본), ALL, VERIFIED, MISMATCH, ADDRESS_UNVERIFIED, REVERSE_FAILED,
NO_COORDINATE, STALE, UNASSESSED입니다. REVIEW는 VERIFIED를 제외합니다.
검색어는 최대 100자로 화장실명·관리번호·도로명/지번을 조회하며 SQL 와일드카드는 문자 그대로 처리합니다.
목록은 판정 시각 오름차순, 동률이면 ID 순입니다. 대용량 JSON과 전체 이력은 목록 응답에 포함하지 않습니다.

## 4. 안전한 수동 처리

[관리자 행정구역 검토 화면](https://admin.geupddong.com/regions.html)에서 필터 → 시설 선택 → 근거/지도 확인 → 좌표 후보 선택 → 사유 입력 → 확정 순서로 처리합니다.

1. 현재 위치와 승인 후보를 구분하며 후보 초기화를 지원합니다.
2. 좌표 없는 시설은 지도 기본 중심점을 저장 후보로 간주하지 않습니다. 관리자가 지점을 선택해야 합니다.
3. 서버는 행 잠금 후 조회 당시의 좌표·두 주소(`expectedLocation`)와 현재 값을 비교합니다.
4. 변경되었으면 409로 거절합니다. 이 경우 역지오코딩과 DB 수정은 수행하지 않습니다.
5. 일치하면 기존 `CoordinateQualityService`로 좌표를 확정하고 서버가 도로명/지번을 각각 조회합니다.
6. 주소 조회 실패 시 저장을 롤백합니다. 성공 시 ADMIN_CONFIRMED 보호, 좌표 변경 이력, 감사 로그를 남깁니다.
7. 변경된 소스의 이전 판정은 STALE로 구분하며 워커가 새 행정구역을 판정합니다.

지역 코드를 임의 입력하거나 강제 VERIFIED로 처리하는 기능은 없습니다.
공급자 코드 충돌은 근거가 해결되지 않으면 미해결로 남깁니다.
주소 오타 수정만으로 좌표를 다시 생성하지 않습니다.
관리자 확정 좌표·주소는 공공데이터 동기화의 덮어쓰기 대상에서 보호합니다.

## 5. 워커·성능

운영 워커는 초기 지연 60초, 실행 완료 후 5분 간격, 실행당 최대 100건,
외부 호출 초당 1회 및 영속 일일 예산 1,000회를 사용합니다.
재판정은 동기 응답이 아니며 대기량·예산·API 장애에 따라 지연될 수 있습니다.

기존 지역/검토/이력 인덱스를 재사용합니다.
원본과 비교해 계산하는 상태는 단순 status 인덱스만으로 해결되지 않을 수 있습니다.
운영 SELECT 검증의 집계/목록 왕복은 약 314/270ms였으나 단일 측정이며 SLA가 아닙니다.
데이터 증가 시 실행계획·p95 지연을 다시 확인합니다.

## 7. 실제 수행한 검증

| 검증 | 결과 |
| --- | --- |
| 관리자 검토 API 테스트 | 85건 중 81 통과, 기존 Docker 필요 4건 제외; 빌드 성공 |
| 관리자 Java 테스트 | 5 통과, 기존 외부 수동 테스트 1건 제외; bootJar 성공 |
| 기존 관리자 JS 회귀 | 6건 통과 |
| 신규 관리자 모의 브라우저 | 비로그인·일반 사용자·데스크탑·모바일·충돌 5개 흐름 통과 |
| 운영 MySQL SELECT | 원본 서비스 CASE SQL, 합성 10건과 실제 목록·집계·이력 검증; 쓰기 0 |
| 실제 관리자 브라우저 | 권한 로그인, 검토 1,597·좌표 없음 1,288 조회, 시설 상세·이력·Kakao 지도 표시 확인 |
| 배포 상태 | API health UP, 공개 조회 200, 익명 관리자 API 401, 관리자 JS 소스 해시 일치 |
| 정규화 선행 검증 | Batch 70건 통과, 격리 MySQL DDL·복구, 제한 적재 및 전체 replay |
| 사용자 주소 표시 | 단위 10건·모바일/데스크탑 모의 8개 시나리오, lint·build 통과 |

모의 브라우저의 저장은 mock으로 검증했습니다. 실제 관리자 브라우저에서는 정상 데이터를 시험 목적으로 수정하지 않았습니다.
실제 Kakao SDK 표시 확인과 실제 좌표 수정의 E2E 완료는 다른 항목입니다.

## 8. 남아 있는 확인

- [ ] 실제 수정이 필요한 사용자 제보 접수 → 관리자 승인 → 워커 재판정 확인
- [ ] 그 이후 정기 공공데이터 배치가 관리자 확정 좌표·두 주소를 보존하는지 확인
- [ ] 개별 미확정/좌표 누락 대상의 운영자 검토(기능 배포와 데이터 해결은 구분)
- [ ] 이력 증가량·장기 보관/파기 정책 및 별도 장치의 암호화 백업 점검

실제 제보가 준비되기 전에는 임의의 좌표나 제보를 만들어 운영 데이터를 바꾸지 않습니다.
WBS는 완료되지 않은 확인 항목을 열어 두고 추적합니다.
