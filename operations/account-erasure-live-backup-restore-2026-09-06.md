## 검증 방식

[독립 복원 스크립트](scripts/verify-live-backup-isolated.py)를 새 소유자 전용 임시 디렉터리에서 실행했다.

- 명시적으로 지정한 파일과 checksum을 대조했다. 다른 백업을 자동 선택하거나 원본을 덮어쓰지 않는다.
- 운영 MySQL의 실제 image ID를 읽어 같은 로컬 이미지를 사용했다. 새 이미지 pull 없음.
- 난수 이름/소유 라벨의 일회용 Docker 컨테이너, `network=none`, 호스트 포트 없음, CPU 1개/메모리 1 GiB로 제한했다. 운영 데이터 디렉터리·키 파일을 컨테이너에 마운트하지 않았다.
- 임시 난수 root 비밀번호는 메모리 환경으로 전달했다. 값이나 Docker 환경 전체를 출력하지 않았다.
- event scheduler는 DISABLED, binlog/LOCAL INFILE은 OFF, secure_file_priv는 NULL로 확인했다.
- 기존 키를 서버에서 읽어 복호화 → gzip 해제 → 임시 MySQL로 직접 파이프 전달했다. 평문 SQL을 호스트 파일로 저장하지 않았다.
- 복원 후 테이블별 건수와 복합 외래키를 포함한 13개 참조 관계를 검사했다. 회원 개별 정보는 조회/출력하지 않았다. 일부 컬럼이 NULL인 복합 외래키는 MySQL의 참조 검사 기준에 맞춰 제외했다.
- 성공/실패 모두 이번 실행의 container ID와 소유 라벨을 확인하고 제거했다. 익명 데이터 volume이 남지 않은 것도 확인했다.

별도 R2 파기 대장 재생, 개인정보 파기, Redis 세션 무효화는 수행하지 않았다. 임시 DB를 운영에 연결/승격하는 기능은 없다.

## 최초 시도와 재검증

최초 실행은 23:25:12~23:30:24 KST에 `backup-import` 단계에서 중단됐다. 초기 코드의 300초 대기 제한, 경과시간, 오류 로그 0 bytes를 근거로 적재 시간 제한에 도달한 것으로 판단했다. 최초 결과에는 예외 유형이 없어 재검증 코드부터 TIMEOUT 분류를 추가했다. SQL/복호화 오류는 발견되지 않았고 원본 hash는 그대로였으며 임시 컨테이너는 제거됐다. 실패 기록은 성공 결과로 덮어쓰지 않고 별도로 보존했다.

재검증에서는 일회용 DB에 한해서 적재 중 `innodb_flush_log_at_trx_commit=2`를 사용하고 적재 제한을 15분으로 늘렸다. 적재가 끝난 뒤 값을 1로 원복하고 `FLUSH ENGINE LOGS`를 실행한 후 검증했다. 두 번째 실행은 약 45초에 완료됐다.

운영 MySQL의 내구성/성능 설정은 변경하지 않았다. 이는 백업의 복원 가능성을 확인하는 검사이지 장애 중 전원 차단 내구성 시험이나 운영 성능 측정은 아니다.

## 자동 정리 기준을 아직 확정하지 않은 이유

1. 선택한 백업에는 `.metadata.json`이 없다. 파일명/mtime을 실제 캡처 시작 시각으로 간주하거나 DB 복원 세대를 임의로 채우지 않았다.
2. 복원된 백업에 `account_withdrawal` 테이블이 없었다. V1.11 회원 파기 재적용을 수행할 스키마가 아니다.
3. 백업 이후 운영 스키마가 바뀌었을 가능성도 확인하기 위해 운영 DB에 **information_schema SELECT만** 실행했다. 현재 운영에도 `account_withdrawal`, `app_user.auth_version`, `audit_log.actor_erased`가 모두 없는 것을 확인했다.
4. 실제 R2 대상 집합과 독립 체크포인트 최초 기준은 이번에 검증하지 않았다. 빈 GitHub 저장소나 미적용 스키마를 근거로 기대 대장 건수를 임의로 0으로 등록하지 않았다.

따라서 결과는 `STRUCTURE_VERIFIED_NOT_ERASURE_CLEARED`, `retentionEligible=false`, `erasureReplayVerified=false`다. 운영 파기 기능이나 자동 정리를 활성화하면 안 된다.
