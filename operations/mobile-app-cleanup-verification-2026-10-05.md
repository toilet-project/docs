# 네이티브 앱 미사용 코드 정리·검증 · 2026-10-05

Android·iOS 앱의 현재 로컬 소스를 기준으로 사용하지 않는 코드만 정리했다. 테스트·타입 검사·양쪽 JavaScript 번들·Android ARM64 설치 후보 빌드와 서명 검증을 통과했다. Android 에뮬레이터에 데이터 삭제 없이 ARM64 후보를 업데이트 설치했고 사용자가 앱 실행을 확인했다. 앱 출시 연기로 사용자의 지시에 따라 이번 정리·Android 실행 확인 범위의 [WBS #124](https://github.com/toilet-project/docs/issues/124)를 완료 처리했다. 주요 흐름 전체·실제 휴대폰·iOS 네이티브의 전반 검토는 미검증이며 완료 범위에서 제외한다. 별도 앱 후속 WBS는 생성하지 않는다.

## 변경과 보존 범위

- 계정·프로필·지도·알림·리뷰의 9개 파일에서 미사용 변수·가져오기 12곳을 정리했다. 번역 훅 호출과 실제 사용 중인 언어·날짜 표시는 유지한다.
- 현재 지도는 로컬 SQLite 카탈로그를 사용한다. 호출되지 않는 `MapAreaCache`, `loadCachedMapArea`, `bufferedMapArea`와 이전 만료·취소 보조 코드만 삭제했다.
- 같은 파일의 `MapArea`, `containsArea`, `completeMarkers`, `sameBounds`, `viewportToilets`, `areaCount`는 유지한다. 집계 마커의 중심점을 조회 범위로 오해해 개수를 추정하지 않는 보호도 그대로다.
- 기본 타입 검사에 `noUnusedLocals`·`noUnusedParameters`를 포함했다. 삭제한 캐시의 테스트는 실제 사용 중인 지도 개수·범위·중복 ID·경계 좌표 검증으로 교체했다.
- 12개 파일에서 118줄을 삭제하고 37줄을 추가했다. 실행 소스의 순감소는 49줄이며 테스트 정리까지 포함한 순감소는 81줄이다. 기능 속도나 설치 파일 감소를 입증한 수치로 해석하지 않는다.

회원·시설 API, 인증·광고·권한 설정, 카탈로그와 저장소 스키마는 변경하지 않았다. 정리 시 직접 작성한 네이티브 모듈 19개 파일의 원본 해시가 동일함을 확인했으며, 후속으로 지도 모듈의 Gradle 빌드 형식 검사를 추가했다. Android Kotlin·iOS Swift 실행 소스는 변경하지 않았다. 공유 게임 코드와 복구용 도구는 보존한다.

## 복구와 코드 관리

앱에 원격 저장소가 없어 현재 소스의 로컬 Git 기준 커밋과 별도 정리 브랜치를 만들었다. 직접 작성한 모듈의 Android·iOS 하위 디렉터리가 제외되지 않도록 무시 규칙을 프로젝트 루트의 생성 폴더에만 적용했다. 비밀 설정·서명 파일·생성 결과·내장 카탈로그 DB는 커밋하지 않았다. 앱 코드는 문서 저장소에 업로드하지 않았다.

정리 변경은 하나의 코드 커밋으로 분리했다. 문제가 확인되면 해당 커밋만 되돌려 기존 앱 설정·다른 기능 소스·카탈로그를 보존한다. 시험 설치 파일은 기존 파일을 덮어쓰지 않고 별도로 보관한다. 원격 저장소 개설·스토어 배포는 이번 작업에 포함하지 않았다.

Android 오프라인 빌드는 기존 `expo-audio`가 필요로 하는 Media3 라이브러리의 캐시가 없어 실패했다. 선언된 버전을 내려받은 뒤 정상 빌드했으며 앱 의존성 선언·잠금 파일은 변경하지 않았다. 기존 Gradle 사용 중단 예정 경고는 남는다.

## 설치 후보의 중요한 차이

시험 후보는 현재 로컬 소스 전체를 포함한다. 이전에 보관한 0.1.53 APK는 이 소스보다 오래됐으며, 현재 소스에는 정리 전에 이미 `expo-audio`와 관련 기능이 포함돼 있었다. 새 후보에는 이 기존 의존성이 선언한 `android.permission.MODIFY_AUDIO_SETTINGS`가 추가로 포함된다. 이번 정리에서 권한 설정이나 오디오 의존성을 변경한 것은 아니다. 이전 APK 대비 크기·네이티브 라이브러리 차이를 미사용 코드 정리의 효과로 판단하지 않는다.

후보는 기존 시험용 서명 인증서를 사용하는 0.1.53 ARM64 APK이며 스토어 배포용 서명이 아니다. 동일한 패키지·서명을 확인했으며 에뮬레이터 업데이트 후 최초 설치 시각이 유지됨을 확인했다. 업데이트 뒤 로그인·언어·저장 데이터의 개별 보존 항목은 아직 직접 대조하지 않았다.

## 에뮬레이터 종료 원인과 재발 방지

처음 만든 x86 전용 APK에는 카카오 지도의 `libK3fAndroid.so`가 없었다. 설치 자체는 성공했지만 지도 사전 준비 중 `UnsatisfiedLinkError`로 앱이 종료됐다. [카카오 SDK 지원 조건](https://apis.map.kakao.com/android_v2/docs/getting-started/)과 현재 SDK AAR에서 ARM 두 형식만 제공하는 것을 확인했다. 에뮬레이터가 ARM64 실행을 지원함을 확인한 뒤 기존 앱과 같은 ARM64 후보로 교체했고, 사용자가 앱 실행을 확인했다. 잘못된 x86 파일은 설치 후보에서 제외했다.

- Expo의 Android 기본 빌드 형식을 ARM64로 지정했다. 기존 생성 Android 프로젝트에도 같은 설정을 적용했다.
- 지도 모듈의 Gradle 설정은 x86 또는 알 수 없는 형식이 요청되면 즉시 실패한다. x86 명시 빌드의 거부와 기본 ARM64 후보 빌드를 검증했다.
- `pnpm verify:android-apk <release.apk>`는 실제 설치 파일의 모든 네이티브 형식에 지도·React Native·Hermes·앱 모듈·Expo·SQLite 라이브러리가 있는지 확인하고 release 번들도 검사한다. 큰 카탈로그를 압축 해제하거나 파일을 변경하지 않는다.
- 정상 ARM64 후보의 검사 통과와 실제로 종료를 일으킨 x86 파일의 검사 실패를 확인했다. 빌드 성공만으로 실행 인수를 완료하지 않는다.

차단 검사를 적용한 기본 빌드 결과와 사용자가 실행을 확인한 ARM64 후보를 비교했다. ZIP 내부에서 바뀐 항목은 기본 빌드 형식이 추가된 `assets/app.config` 하나이며 JavaScript 번들·네이티브 라이브러리·클래스·내장 DB는 동일하다. 사용자 확인 결과를 새 기능 전체나 실제 휴대폰 성능 검증으로 확대하지 않는다.

에뮬레이터에서 ARM64를 실행할 수 있다는 확인은 실제 휴대폰의 지도 성능이나 모든 에뮬레이터에서의 동작 보장이 아니다. SDK·Hermes 버전 또는 네이티브 제공 파일이 바뀌면 설치 파일 검사도 함께 검토한다.

## 완료 범위에서 제외한 출시 전 검토

기존 로그인·언어·저장 데이터의 업데이트 후 개별 대조, 위치 권한·백그라운드 복귀, 지도·검색·다국어·계정·리뷰·제보·알림의 주요 흐름 전체, 광고·오디오·쓰기 동작과 실제 휴대폰·iOS 네이티브 인수는 미검증이다. 사용자가 출시 전에 전반 검토할 예정으로, 현재 정리 작업의 남은 항목이나 별도 후속 WBS로 추적하지 않는다.

자동 검사는 실제 회원 데이터를 변경하지 않았다. 향후 저장·읽음 처리·광고·소셜 인증을 검증할 때는 확인한 범위를 별도로 기록한다.
