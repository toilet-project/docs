## 환경과 범위

- 운영과 같은 이미지의 MySQL **8.0.46** 사용.
- 전용 컨테이너 `toilet-region-v10-check-9lm3gi`, 네트워크 none, 호스트 포트 없음, 전용 tmpfs, CPU 1·메모리 512MiB.
- 운영에서는 `SHOW CREATE TABLE toilet`, Flyway 적용 버전, 데이터 건수/검증 지문만 읽었다. 운영은 V0 baseline 및 V1~V7 성공 상태다.
- 운영 toilet의 실제 DDL을 격리 DB에 생성한 뒤 저장소 V1~V10 SQL을 번호순 실행했다. V8 직전에 합성 화장실 4건·사용자 1건·제보 1건·좌표 이력 1건을 넣어 기존 행 보존을 검사했다.
- SQL 직접 실행 검증이며, **실제 운영 데이터 전체 복제·Spring Boot/Flyway 애플리케이션 기동 검증은 아니다.** 운영 V1~V7을 재실행하지 않는다.

## 통과 항목

1. V1~V10 SQL 순차 실행 성공.
2. V9 기존 제보·확정 도로명 보존, 새 지번 컬럼 NULL, 지번만 반환된 확정 이력 저장 가능.
3. V8 현재 view에 좌표와 원본이 일치하는 VERIFIED만 노출. 좌표 변경·주소 변경·미확정 상태에서 즉시 제외.
4. V10 같은 결과 재적용 중복 방지, JSON 세부 사유와 시각 밀리초 보존.
5. 트랜잭션 rollback 시 새 판정 이력과 현재 결과 수정 모두 취소.
6. 관리자 상태별 목록은 `idx_toilet_region_review`, 화장실별 이력 조회는 `idx_region_assessment_toilet`을 사용하는 EXPLAIN 확인.
7. 합성 이력/좌표 수정 데이터를 별도 테스트 백업 테이블에 보존한 후 V10/V8 구조 제거 및 V9 역변경 성공. 원래 화장실 4건의 주소·좌표·출처 보존.
8. 모든 assertion 통과: `ALL_ASSERTIONS_PASSED`.

인덱스 검증은 소량 합성 데이터의 실행 계획 확인이다. 운영 데이터 전체 적재 후 성능·실행 계획은 별도 확인한다. V9 적용 후 지번만 존재하는 신규 이력이 있으면 도로명 NOT NULL로 단순 롤백할 수 없다. 운영에서는 새 컬럼/이력을 보존한 채 이전 실행 파일로 복귀하는 방식을 우선한다.

## 전체 분석 준비

- 전체 조회 대상 53,576건 중 좌표 있는 52,288건을 우선 역지오코딩한다. 좌표 없는 1,288건은 관리자 좌표 입력 대기로 분리하고 자동 좌표 채움은 하지 않는다.
- 새 v2 체크포인트 기준 서로 다른 좌표 42,643회 기본 호출. 예외 추가 조회/재시도는 별도이므로 확정 총 호출량이 아니다.
- 초당 1회 기준 기본 요청 간격만 약 11.85시간. 표본의 추가 호출 비율을 적용하면 약 4.7만 회/13시간 수준이며 대기·시작 비용·예외에 따라 더 늘어난다.
- 카카오 공식 안내의 일간 무료 쿼터는 주소 검색/좌표→행정구역/좌표→주소 각 100,000회다. 계정/앱별 무료 적용 조건과 실제 사용량은 앱 관리 화면에서 확인해야 한다. [공식 쿼터](https://developers.kakao.com/docs/ko/getting-started/quota)
- 브라우저 개발자 사이트가 로그아웃 상태라 **앱 실제 잔여 쿼터와 유료 설정은 아직 확인하지 못했다**. 사용자 로그인 요청 후 대기 중. 전체 외부 API 분석은 시작하지 않았다.
- 운영 migration/apply/main push/배포는 미수행. 코드 검토·승인은 별도다.
