확인 시 mtime 경과는 약 0.01~6.16일이며 14일 초과 표시는 없다. **mtime/파일명은 참고값이며 캡처 시각이나 법적 보유 기간을 대신하지 않는다.** metadata 없는 파일에 이 값을 소급 기록해 자동 정리를 통과시키지 않는다. 같은 크기 또는 근접 생성 시각을 근거로 중복이라고 판단하지 않는다.

## 보존과 정리 순서

1. 현재는 11개 모두 보존한다. 새 복원 검증본과 앞서 복원한 기존 `20260905-181509` 파일을 검토 과정의 보호 대상으로 유지한다.
2. 03:15 새 백업 생성 후 service 종료 0, 덤프/checksum/metadata 3개, 현재 DB 세대·UUID·파일 hash·캡처 시각 일치를 확인한다. 생성됐다는 사실만으로 복원 검증 hash 설정을 갱신하지 않는다.
3. 새 정기 백업의 실제 격리 복원을 승인된 범위에서 확인한 뒤 최근 복원 검증 증빙을 갱신한다. 현재 보호 hash는 00:35에 검증한 파일을 가리킨다.
4. 기존 파일별 생성·보관 맥락과 필요한 복구 시점을 확인한다. metadata 없는 파일은 현재 자동 정리 도구에서 계속 HOLD_LEGACY_METADATA이며, 별도의 legacy 처리 정책/도구 검토가 필요하다.
5. 정리가 필요할 때 정확한 파일명·hash·동반 checksum·보존할 복원본을 담은 **새 삭제 계획**을 만들고 승인받는다. 최신 목록·작업 잠금·복원 사용 여부를 다시 확인하며, 폴더 전체 삭제나 mtime 기반 일괄 삭제는 금지한다.
6. 단계적 전환이 길어지면 원래 목표 보관 기간과 충돌하므로 방치하지 않는다. 검토 대상이 아직 오래되지 않았다는 이유로 무기한 보관하지 않는다.

metadata가 있는 신규 백업도 14일 경과만으로 바로 삭제하지 않는다. 최근 복원 검증·DB 식별·계획 hash·작업 배제 등의 기존 안전 조건이 필요하다. 이 문서는 삭제를 허가하지 않으며 특정 미래 날짜에 자동 삭제하도록 예약하지 않았다.

## 예상되는 점검 결과와 남은 작업

- 04:15에 legacy metadata 보류가 다시 나오는 것은 예상 가능하다. 다만 실제 실행 결과는 그 시각 이후 확인해야 하며 지금 성공/실패로 단정하지 않는다.
- 첫 수동 보류 알림 이후 6시간 이내라면 같은 상태는 알림이 억제될 수 있다. Discord 메시지 유무만으로 timer 미실행을 판단하지 않는다.
- 현재 최근 복원 검증 파일은 약 36시간 신선도 조건이 있다. 실제 복원 시험 없이 새 파일 hash로 대체하지 않으며, 검증 갱신이 없으면 별도 보류가 발생할 수 있다.
- 전체 binlog/Redis/외부 사본 범위와 회원 자동 파기·지속 체크포인트 갱신은 이 파일 목록 점검으로 완료되지 않는다.
