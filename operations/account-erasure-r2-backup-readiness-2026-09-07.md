# R2·독립 기준·백업 운영 준비 점검

2026-09-07 KST. 운영 DB/백업/R2 객체 변경 및 파기 활성화는 수행하지 않았다.

## 읽기 전용 R2 검사

배치 feature `658de90`에 `ErasureReadinessLiveTest`와 전용 workflow를 추가했다. 기존 가상 객체 생성·삭제 검사는 재실행하지 않았다.

- 기존 검증에서 사용한 계정 endpoint와 전용 버킷으로만 접속한다.
- GitHub Secrets는 검사 단계에서만 전달하고 로그/보고서에 값·지문을 출력하지 않는다.
- 암호화 키링 형식/k1을 확인하고 HEAD bucket, LIST 최대 1건을 전체 버킷·운영 의도·운영 catalogue 경로에 각각 수행한다.
- 객체 내용 다운로드·복호화·생성·삭제, DB·Redis 연결은 없다.
- 출력은 접근 성공과 존재 여부뿐이다. 전체 목록의 무결성 검사나 독립 기준 생성이 아니다.
- 로컬 컴파일 성공. 로컬은 실행 조건이 없어 live 검사 1건 건너뜀이며, R2 성공으로 계산하지 않는다.

실제 검사 결과: [최초 검사](https://github.com/toilet-project/toilet-batch/actions/runs/34042213830) 성공. 출력 접근성을 보완한 `dc8d0cc`의 [재확인](https://github.com/toilet-project/toilet-batch/actions/runs/34042313395)도 성공했다(2026-09-07 00:27 KST). 접근 정상, 현재 버킷 객체 없음, 운영 의도·catalogue 객체 없음으로 관측됐다. `baselineEstablished=false`, 객체 내용 읽기/쓰기 false를 유지했다. 빈 관측이 과거 유실 부재나 독립 초기 기준을 증명하는 것은 아니다.

새 workflow의 checkout/setup-java v4 사용에 대한 Actions 지원 종료 안내 경고가 있었다. 검사 실패는 아니며, 기존 CI 도구 버전 갱신은 별도 정비 대상으로 남긴다.

## 독립 체크포인트

`toilet-project/operations-checkpoints`가 private이며 `checkpoints/`에는 `.gitkeep`만 있는 것을 GitHub API로 확인했다. 실제 운영 기준은 아직 없다.

브랜치 보호 조회는 현재 플랜에서 비공개 저장소 보호 기능을 사용할 수 없다는 HTTP 403을 반환했다. 공개 전환·플랜 변경·권한 확장은 하지 않았다. 검증 CI가 있다는 사실만으로 강제 변경 방지나 불변 대장이 완성됐다고 보지 않는다. 비공개 유지, 제한된 쓰기 권한, 검토 절차를 기본으로 하며 강제 보호 도입은 별도 결정이 필요하다.

조직 Actions variable 조회는 현재 인증 scope 부족으로 403이었다. 조회 권한을 추가하지 않았다. 저장소 수준에서 R2 배포 변수 부재는 확인했지만 조직 공급원까지 없다고 단정하지 않는다. 배포 승인 변수는 설정하지 않았다.

## 운영 DB·런타임 재확인

- Flyway baseline 0, V1~V10 성공, V11 없음.
- 현재 API·배치 컨테이너에 신규 retention/erasure/ledger/catalogue 설정 및 R2 자격 증명 환경변수가 없음.
- 이는 준비 중인 feature가 운영 연결된 상태가 아님을 확인하는 자료다. 환경변수 부재만으로 과거 모든 수동 작업 부재를 증명하지 않는다.
- 현재 배치 Redis 설정은 미배포 상태. 앞선 [네트워크 연결 검증](account-erasure-redis-readiness-2026-09-07.md)과 구분한다.

## 다음 운영 전환에 필요한 결정

1. 키링 원문의 별도 보관은 2026-09-07 운영자가 확인했다. 값은 채팅·문서로 받지 않았다. 이는 보관 사실에 대한 운영자 확인이며 별도 사본으로 실제 복호화 복구를 시험한 결과는 아니다.
2. 초기 기준: R2 관측, 독립 기록, 기존 기능 미배포·수동 작업 이력을 함께 검토하고 DB 복원 세대를 정한다. 빈 버킷 관측값을 자동 기준으로 등록하지 않는다.
3. 승인된 설정으로 새 백업 metadata 생성과 독립 점검/실패 감시를 함께 설치·검증한다. 기존 백업에 metadata를 임의 보충하지 않고, 기존 만료 삭제 제거에 따른 운영 대응도 함께 확정한다.
4. 기존 백업·binlog·Redis·외부 사본 범위를 확정한다. 이 점검은 지정 MySQL 백업 경로만 확인했다.
5. 웹 정책/점검 시간과 API Flyway V11 단일 적용을 승인한 후 배포한다. 자동 파기 활성화는 선행 조건 확인 뒤 별도 단계다.

현재 완료 범위는 검사 도구 및 준비 상태 확인이다. 운영 대장 초기화·백업 체계 전환·자동 파기 완료로 표시하지 않는다.

## 별도 키 보관 확인 후의 단계별 적용안

후속: 1~2의 1회 실행은 사용자 승인 후 완료했다. [신규 metadata 백업·격리 복원 결과](account-erasure-metadata-backup-rehearsal-2026-09-07.md)를 참조한다. 아래 3~4와 운영 배포/자동 파기는 아직 미실행이다.

처음 적용안을 다음 범위로 나눴다. 1~2의 후속 완료 여부는 위 결과를 우선하며, 기존 정기 백업은 교체하지 않았다.

1. **메타데이터 백업 1회 검증**: 새 백업 스크립트/도구를 별도 비공개 경로에 준비하고, 검토한 DB 복원 세대를 사용해 암호화 백업 1건과 checksum/metadata를 생성한다. 기존 스크립트·timer·과거 백업은 그대로 둔다. 기존 MySQL에 mysqldump 읽기 부하와 추가 디스크 사용이 발생한다.
2. **격리 복원 확인**: 새 백업을 외부 트래픽에 연결하지 않는 임시 MySQL로 복원하고 metadata/DB 식별·전체 스키마·가상 파기 계약을 검증한다. 운영 회원은 시험 변경하지 않으며 실제 파기 대장이 비어 있는 검증을 비어 있지 않은 대장의 재생 시험으로 과장하지 않는다.
3. **초기 독립 기준 검토**: 운영 파기 기능 미배포, 빈 R2 관측, 수동 파기 대장 작성/유실 여부를 함께 확인한 뒤 복원 세대와 초기 집계 기준을 비공개 저장소에 기록한다. 이 단계의 기록도 별도 승인하며 유료 보호 기능 제한을 명시한다.
4. **정기 백업 체계 전환**: 1~3의 결과와 기존 만료 정리 영향·보류 대응·오래된 metadata 없는 백업 처리 방침을 검토한 후 새 백업과 독립 dry-run 점검/실패 감시를 함께 설치한다. 이전 스크립트는 기존 성공 후 자동 정리 동작이 있으므로 신·구 방식을 무기한 혼용하지 않는다. 새 timer만 설치해 자동 만료가 완성됐다고 표시하지 않는다.

1회 백업/격리 검증 승인은 정기 timer 교체, 초기 기준 확정, Discord 추가 전송, 기존 백업 삭제, API 배포나 회원 자동 파기 활성화까지 포함하지 않는다.
