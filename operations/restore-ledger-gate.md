# 정기 격리 복원과 실제 파기 대장 검증

## 범위

기존 정기 백업 복원 점검에 실제 운영 파기 대장과 독립 체크포인트 검증을 연결한다.
원본 백업을 바꾸거나 운영 DB를 복원·파기하지 않는다. 이 점검의 성공은 특정 시점의
격리 복원 검증이지, 운영 복원 승인 또는 백업 삭제 허가가 아니다.

탈퇴·계정 복구·자동 파기 활성화와 기존 백업 정리는 별도 인수 항목으로 유지한다.

## 처리 순서

1. 기존 백업 잠금을 획득하고, 독립 서버 UUID·DB 세대가 일치하는 최신 캡처를 선택한다.
   메타데이터 없는 예전 백업은 정상으로 간주하지 않는다. 최신 캡처가 36시간을 넘으면 중단한다.
2. API와 배치의 실제 실행 설정에서 필요한 키만 메모리로 읽는다. US 저장소·운영 realm·DB 세대,
   두 서비스의 설정 일치와 실행 상태를 확인한다. 비밀값을 출력하거나 점검 파일에 저장하지 않는다.
3. 운영 MySQL과 동일한 이미지로 외부 포트 없는 임시 DB를 만든다. 전용 내부 네트워크와 무작위
   표식·서버 UUID·별도 DB 포트로 운영 DB 오접속을 차단한다. 이벤트·binlog·local infile을 끈다.
4. 암호화 백업을 파이프로만 복호화·복원한다. 테이블과 외래키 참조를 확인한다. 정기 모드는 V11이
   이미 있는 백업만 처리하며 V11을 대신 설치하지 않는다.
5. 비공개 GitHub의 독립 체크포인트와 R2의 intent·catalogue를 읽는다. DB 세대·건수·전체 목록
   해시가 모두 같아야 한다. 체크포인트 건수 + 1을 상한으로 조회하여 누락·초과를 차단한다.
6. 동일한 백엔드 `AccountErasureRestore`로 격리 DB에서 dry-run → 적용 → 재적용을 수행한다.
   이미 사라진 회원은 부재로 계산한다. 회원 ID와 생성 시점이 충돌하면 실패한다. 두 번째 적용은
   삭제 0건이어야 하며 화장실·제보·좌표 이력의 건수와 외래키 참조도 다시 확인한다.
7. 실제 대장·체크포인트를 다시 읽어 같은 스냅샷인지 확인한다. 원본 백업과 메타데이터가 변하지
   않았는지 확인하고, 이번 실행이 만든 컨테이너·볼륨·네트워크만 정리한다.
8. 부모 점검에서 서비스 설정과 실제 대장을 한 번 더 확인한 뒤에만 보호 백업 해시와 집계 영수증을
   기록한다. 구조만 통과한 예전 결과는 정기 점검의 성공으로 사용할 수 없다.

## 실패 판정

- 키 누락, API·배치 설정 불일치, 기존 DB 세대와의 불일치: 복원 실행 중단.
- R2 또는 GitHub 접근 실패, 목록·해시·건수 불일치, 검사 중 대장/배포 변경: 성공 승격 금지.
- 파기 대상 ID 재사용/생성 시점 충돌, SQL 오류, 재적용 실패, 외래키 오류: 실패.
- 격리 컨테이너·볼륨·네트워크 정리 실패: 실패, 수동 확인 필요.
- 복원 실행 이후 실패하면 기존 failed-run 표식을 남긴다. 다음 정기 실행은 수동 점검 전까지
  재진행하지 않는다. 기존 systemd OnFailure 알림 경로를 유지한다.
- 외부 서비스 일시 오류도 정상으로 우회하지 않는다. 오류 원문·회원 정보·키 대신 실패 단계만 남긴다.

## 성공 영수증

백업 및 메타데이터 해시, 캡처/검증 시각, DB 세대·서버 식별자, 체크포인트 해시·시퀀스,
대장 건수 및 집계 목록 해시를 비공개 로컬 영수증으로 남긴다. 회원별 목록과 개인 정보는 제외한다.
`productionLedgerReplayVerified=true`는 격리 복원본에서 그 시점의 실제 대장을 검증했다는 뜻이다.
`retentionEligible=false`와 `productionDatabaseModified=false`는 계속 유지한다.

## 코드 구성과 소스 일치

아래는 설치된 구성 요소의 역할 설명이다. 이 공개 문서 변경에는 서버별 설정이 들어 있는 운영 스크립트 원문을 포함하지 않으며, 검증한 원문·해시·되돌리기 자료는 비공개로 보존한다.

- `verify-and-refresh-backup.py`: 기존 정기 진입점, 잠금·강한 증빙 확인·보호 해시 갱신.
- `verify-live-backup-isolated.py`: 기존 격리 복원기에 `--ledger-replay` 모드 추가.
- `restore-ledger-context.py`: 필요한 실행 설정 선택·서비스 동일성 검사·최종 대장 재확인.
- `BackupLedgerReplay.java`: 실제 대장 스냅샷 검사와 격리 DB 파기 적용·재적용.
- `refresh-restore-verification.py`: 새 증빙 형식 검사. 이전 구조 전용 결과를 읽는 호환성은 유지하지만,
  정기 실행 부모는 새 강한 증빙을 필수로 요구한다.

Java 검증기는 배치 PR #43 운영 준비 배포의 공통 계정 소스 12개와 함께 컴파일한다.
기준 main 커밋은 `4c2cb41ecc1f2ec6bffef2c153f8fd620029c6a6`이다.
오래된 도구 라이브러리에 들어 있는 공통 계정 클래스가 우선 사용되지 않도록 새 classes 경로를
라이브러리보다 앞에 둔다. 향후 파기 SQL·스키마가 바뀌면 이 도구도 같은 버전으로 갱신하고 검증한다.

## 안전한 적용·되돌리기

검사 통과 전에는 기존 설치 파일·타이머를 바꾸지 않는다. 임시 폴더에 스크립트·클래스를 배치하고,
실제 백업을 사용하되 보호 설정과 상태 디렉터리는 임시 복사본으로 시험한다.
설치 시 기존 스크립트를 보존하고 실행 중인 정기 점검이 없는지 확인한 뒤 교체한다.
기존 백업·복원·보관 점검 시간과 알림 유닛은 변경할 필요가 없다.

되돌려야 할 때는 우선 정기 검증을 중지하고 원인을 확인한다. 이전 스크립트로 복귀하면 구조만
검증하는 수준으로 돌아가므로 실제 파기 대장 인수까지 완료된 것으로 표시해서는 안 된다.
기존 실패 표식을 자동 삭제하거나, 원본 백업·독립 대장을 되돌리는 방식은 사용하지 않는다.

## 제한과 후속 확인

- 실제 운영 대장이 0건이면 실제 회원이 포함된 대장에 대한 통합 검증으로 표시하지 않는다.
  비어 있지 않은 목록의 정책 검사는 가짜 데이터로 별도 실행한다.
- 점검 중 신규 파기 기록이 생기면 실패·보류할 수 있다. 운영 쓰기를 중지시키거나 락을 추가하지 않는다.
  스냅샷 이후의 파기는 향후 운영 복원 직전에 다시 적용·검증해야 한다.
- 검증마다 대장 전체를 여러 번 읽는다. 현재 상한은 체크포인트 10만 건 및 단계별 실행 시간이다.
  대장이 커져 시간 한도를 넘으면 성공으로 우회하지 않으며, 분할 검증 설계가 필요하다.
- 이 작업은 원본 암호화 백업 속 과거 개인 정보를 삭제하는 작업이 아니다. 보관·파기 정책의
  별도 정리 요건이 해결되기 전까지 예전 백업은 보류 상태로 남는다.
