## DOCS #72 — 키와 토큰 수명주기 계획

### 1. 암호화 키

현재 배포 소스의 ErasureCipher는 AES-256-GCM, 키 ID를 인증한 envelope, 최대 10개 키를 허용한다. active-key는 새 암호화용이며 기존 키로 기존 데이터를 읽을 수 있어야 한다.

1. 운영 키를 변경하기 전에 합성 데이터로 구키 기록 → 신·구키 동시 읽기 → 신키 기록 → 재시작/복구 읽기를 검증한다.
2. 구키 누락, 잘못된 키 ID, 변조, 동일 ID에 다른 키가 들어간 경우는 실패/보류되는지 확인한다.
3. 별도 승인된 변경 창에서 API·batch·복원 도구 모두 구키를 유지하고 신키를 읽을 수 있는 설정을 먼저 적용·확인한다. 뒤이어 쓰기용 active-key를 전환한다.
4. 새 키로 쓴 기록이 생긴 뒤에는 구키만 가진 이전 설정으로 되돌리지 않는다. '배포 롤백'과 '복호화 가능성'을 따로 확인한다.
5. 구키 의존 대장·보존 백업·검토 파일이 존재하는 동안 구키를 제거하지 않는다. 기존 put-if-absent 기록을 무조건 덮어 재암호화하지 않는다.
6. 키 교체·제거는 값이 없는 키 ID/검증 시각/상태 기록으로 남기고, 실제 키 값은 승인된 비공개 보관 경로에서만 취급한다.

**운영 키 교체·구키 제거는 이번 작업에서 미실행.** 최대 10개라는 구현 제한은 10개를 안전하게 모두 사용하는 운영 권고가 아니다. 사용자가 별도 보관한 키만으로 복구하는 검사는 서버 설정의 기존 키를 사용한 성공과 별도로 인수한다.

### 2. 독립 GitHub 인증

- 전용 비공개 저장소 하나의 Contents 읽기·쓰기 범위를 유지한다. 개인 계정 전체 권한, 관리자 bypass, public 전환을 대안으로 사용하지 않는다.
- 비밀값 없는 인벤토리에 소유자, 저장소, 권한, 발급/만료일, 교체 예정일, 검증 결과를 기록한다. 운영 토큰의 지정 저장소 GET은 200, private=true·archived=false였다. 응답의 인증 토큰 만료 헤더는 **2026-10-06 16:10:27 UTC = 10/7 01:10:27 KST**였다. 발급일·전체 발급 범위는 이 조회만으로 확정하지 않는다.
- 저장소 응답의 permissions는 호출 주체의 저장소 관계이며 fine-grained 토큰의 실제 전체 허용 범위를 증명하지 않는다. 응답의 admin=true를 '토큰에 전체 관리자 권한이 있음'으로 단정하지 않는다.
- 만료 사전 알림의 제안 기준은 30/14/7/1일이다. 기존 Tunnel 서비스 토큰의 알림이 이 GitHub 토큰까지 포함한다고 간주하지 않는다. 설치/실제 전송 인수 전 '자동 알림 구현 완료'로 표시하지 않는다.
- 교체는 새 토큰의 같은 범위 읽기 확인 → 모든 writer/복원 도구 반영 확인 → 승인된 시험 경로 검증 → 구 토큰 폐기 순서다. 실제 운영 기준에 시험용 회원 기록을 넣지 않는다.
- GitHub CAS/force=false는 저장소 관리자의 삭제/force-push 권한을 기술적으로 불가능하게 만드는 WORM이 아니다. 보호 정책을 강화할 경우 정상 writer가 차단되지 않는지 별도 격리 검증한다.

### 3. 증가하는 대장과 실행 비용

현재 배포 API 소스(823e60a)의 제한과 구현: ProtectedErasureLedgerFactory → CheckpointedErasureLedger → GitHubErasureHistoryStore가 실제 경로이며, HTTP transport는 GitHubErasureCheckpointStore의 공통 구현을 사용한다. 이전 reader만을 현재 경로로 오인하지 않는다.

| 항목 | 실제 제한/구현 | 대응 |
| --- | --- | --- |
| LOCAL 파일 | envelope 최대 8,192 bytes | 초과/변조를 누락시키지 않고 보류 |
| 암호화 평문 | 최대 8,000 bytes | 검토 파일 등 문서 크기 검증 |
| checkpoint 회원 수 | 100,000 이상이면 추가 선기록 차단 | 파일 저장소의 더 큰 list 상한을 실효 상한으로 오인하지 않음 |
| checkpoint sequence | 100,000 초과 거부 | count와 sequence를 별도로 관찰 |
| GitHub | 연결 3초 / 요청 10초, 응답 최대 8 MiB, 잘린 tree 거부 | timeout/응답 유실은 SQL 파기 성공이 아님 |
| 검증 비용 | 매 처리에서 의도/목록 읽기·digest 대조 및 독립 확인 | 건수 증가 시 처리시간·메모리·GitHub 요청/실패율 측정 필요 |

제안 검토 지점은 count 또는 sequence 50,000 도달, 배치 창 내 완료 불가, 보호 검증 시간의 지속 증가, GitHub 403/429/5xx 반복이다. 이 수치는 새 운영 차단값이 아니라 성능 검토를 시작할 계획 기준이며 현재 모니터에 설치하지 않았다. 실제 실패를 가리거나 보호 검증을 생략하여 처리량을 늘리지 않는다.

확장 검증은 0/1/1,000/10,000건 합성 데이터의 정상/중단/재시도부터 수행하고, 운영과 분리된 환경에서 메모리·시간·요청 수를 기록한다. 분할·세대/증분 구조 변경이 필요하면 기존 대장 호환성과 복원 검증을 먼저 설계한다. 성능 개선을 이유로 기존 개인정보 보호 기록을 임의 삭제하지 않는다.

## 사본/대장 종료와 외부 준비 자원

- binlog가 보관 중이라는 이유만으로 일반 탈퇴 기능 전체를 OFF로 되돌리지 않는다. 복원 보호와 사본 종료 인수는 별도다.
- 자연 만료의 관찰 자료는 전후 목록·동일 DB 식별·설정·기록 시각으로 남긴다. 빈 목록이나 파일 mtime만으로 이벤트/사본 완전 소멸을 인증하지 않는다.
- 개별 대장 종료는 해당 파기 회차의 사본·부재·최신 독립 기준 등 실제 증거와 별도 승인이 필요하다. 현재 자동 종료 OFF 유지.
- 과거 R2 준비 자원은 정확한 버킷/경로·참조 writer·객체 건수·용도를 먼저 읽기 대조한다. 프론트 캐시 버킷과 분리하고, 불명확한 객체는 보존한다.
- 잔여 삭제·키/토큰 폐기·정책 변경은 정확한 대상과 복구 가능성을 설명한 별도 승인 전 수행하지 않는다. 이 문서는 외부 자원 부재 증명이 아니다.
