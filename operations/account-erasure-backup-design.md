# 백업 복원 시 회원정보 재생성 방지 — 설계 및 구현 상태

상태: 2026-09-06 사용자가 Cloudflare R2를 선택했다. 비공개 버킷 생성, 암호화 전송 어댑터·격리 복원 도구의 로컬 구현과 가상 데이터 왕복 검증을 완료했다. 운영 키 연결·실제 회원 전송·운영 활성화는 하지 않았다. [최신 R2 구현·검증 보고서](account-erasure-r2-2026-09-06.md)를 기준으로 진행 상태를 확인한다.

## 기존 백업의 한계

기존 mysql-backup.sh는 암호화된 전체 SQL 덤프를 만들고, mysql-restore-verify.sh는 격리 컨테이너에서 테이블/화장실 건수를 확인한다.
현재 절차는 파기한 회원정보가 과거 백업에서 복원되는 것을 제거하지 않는다.
스크립트 기본 보관 14일은 확인했지만 실제 운영 설정·스냅샷·binlog·외부 사본의 최장 보관 기간은 확인하지 않았다.

삭제 이력을 같은 MySQL DB에만 기록하거나 같은 미니 PC 디스크에만 내보내면 DB/디스크 손실 시 같이 사라진다.
삭제 후 나중에 외부로 보내는 방식에도 전송 전 장애 구간이 있다.

## 권장 처리 계약

1. 기존 회원 잠금과 상태/기한 검사 후, 파기 대상임이 확정된 계정에 대해 최소한의 파기 의도를 별도 저장소에 내구성 있게 기록한다.
2. 외부 기록의 성공을 확인하지 못하면 회원정보의 물리 삭제를 보류하고 재시도한다. 이미 중지된 계정을 다시 로그인/복구 가능하게 만들지 않는다.
3. 기록 확인 후 Redis 정리 및 회원 DB 트랜잭션을 완료하고 결과를 기록한다. 외부 기록 성공 후 DB가 롤백될 수 있으므로 작업은 재실행 가능해야 한다.
4. 백업 복원은 서비스 연결·스케줄러·Redis 연결을 차단한 환경에서 한다. 그 백업 이후 파기 대상 기록을 적용하고 검증한 뒤에만 운영 연결을 허용한다.

이 설계는 DB와 외부 저장소를 하나의 트랜잭션이라고 가정하지 않는다. 외부에 먼저 기록한 파기 의도는 복구를 허용하지 않는 대상에만 발급해야 한다.

## 최소 정보·검증 요구사항

- 이름/이메일/소셜 원문/제보 원문을 저장하지 않는다.
- 회원 ID만으로 적용하면 복원 후 ID 재사용과 혼동할 수 있으므로 원래 계정의 생성 시각과 대상 DB 식별도 검증한다. 구현 필드는 version, realm, userId, userCreatedAt, withdrawalKey, eligibleAt이다. 생성 시각은 실제 DB에 저장된 값을 읽는다.
- 파기 이벤트 식별자·기준 시각·형식 버전 등 최소 정보만 암호화해서 보관하고 위변조 및 누락/전송 실패를 감지한다.
- 최소 기록도 개인과 연결 가능하면 개인정보다. 복원 차단 목적·접근 권한·최대 보관 기간·기간 만료 삭제를 정책에 명시해야 한다.
- 대장 보관 기간은 복원 가능한 백업/복제/로그의 최장 기간과 함께 정한다. 무조건 영구 보관하거나 임의의 기간을 확정하지 않는다.
- 외부 저장소의 쓰기/읽기 권한은 분리하고 공개 업로드하지 않는다. 키는 문서/코드가 아닌 기존 비밀정보 관리 경로로 주입한다.

## 필요한 결정

저장소는 R2로 확정했지만 실제 백업 최장 보관 기간, 삭제 대장 만료·보존 잠금, 암호화 키의 별도 보관, 국외 보관 관련 정책 검토가 남아 있다.
GitHub Secrets를 사용한 실제 Java S3 저장·읽기, API/배치 교차 복호화, [가상 암호화 백업의 격리 MySQL 재파기 통합 리허설](account-erasure-restore-rehearsal-2026-09-06.md)은 완료했다. 미니 PC 런타임 자격 증명 연결·설치와 실제 전체 스키마 백업 리허설은 남아 있다. GitHub 실행 성공을 운영 배포 완료로 간주하지 않는다.
